Workflow

Any task that produces or changes code ticks through this checklist. A failure returns to the step that owns it, never a patch around it.

  1. Confirm target

    Device, subsystem and core, toolchain, host side, timing in ns or cycles.openpru.md · soc-am335x.md

  2. Plan registers and cycles

    Fill the register map and cycle budget templates before writing code.timing.md · isa-quick-ref.md

  3. Write the code

    Conventions: lowercase mnemonics, .set constants, m_ macros, FN_ functions, cycle comments, end with halt.c-interop.md if C is linked

  4. Lint

    Column-1 mnemonics, immediate ranges, register fields, labels, missing halt, per-function register use, macros and includes, OpenPRU headers.scripts/lint_pru.py

  5. Build

    OpenPRU makefiles, or build.sh for AM335x and standalone files. No flag changes.scripts/build.sh · clprufail → step 3

  6. Simulate

    Run to halt or a condition, check registers, memory and pins. Skip with a stated reason if unmodelled.scripts/simulate.py runwrong → step 3

  7. Verify timing

    Compare each critical path to its budget. Under about 5% margin, recommend a hardware check.simulate.py edges · timing.mdover budget → step 2

  8. Build MCU+ project

    OpenPRU devices: BUILD_MCUPLUS=y, then gmake -s, so the R5F app embeds the PRU firmware. Flash only if asked. No deploy script.openpru.md

What each script does

lint_pru.py

step 4 · no install

Static checks the TI assembler misses or reports one error at a time. It reports every problem in a file in one pass.

read .asm→strip comments, parse labels, .set symbols, functions and macros→check instructions, register use and includes→print file:line: error|warning [rule]
$ python3 scripts/lint_pru.py [--openpru] [--c-abi] [-I dir] file.asm
bad.asm:2: error [immediate] ADD operand 3 = 300 is outside OP(255)
bad.asm:3: error [label] QBNE target 'nowhere' is not defined in this file
bad.asm:0: warning [nohalt] no HALT and no return (JMP r3.w2 / RET) found
bad.asm:4: warning [PRU-M001] 'mymacro' is not an instruction and no macro ...
bad.asm: 2 error(s), 2 warning(s)          # exit 1
RuleChecks
column1, immediate, register, labelErrors: mnemonic in column 1, literal outside operand range, invalid register or field, branch to undefined label
extern, r31event, nohaltWarnings: unresolved JMP/CALL symbol, R31 write without bit 5, no halt or return
PRU-C001 · C003 · C004Per function: read before write (header-named inputs count), discarded write, and with --c-abi r4–r13 written but never read
PRU-M001 · M003 · M004 · M005Macros and includes: undefined macro, self-invoking, redefined with a different body, unresolved .include (search folders via -I)
tab, width, todo, include, PRU-D001–D003--openpru only: style rules and function or macro headers (Description, PEAK cycles, Parameters, Registers modified, Returns, Pseudo code)

Exit 0 clean, 1 errors, 2 usage. Examples of ranges it knows: ALU immediates 0–255, shifts and bit ops 0–31, ldi 0–65535, byte counts 1–124, loop 1–256. Every warning needs a fix or a one-line reason.

build.sh

step 5 · needs clpru

Compiles each source with clpru, then links with your linker command file. Run it unchanged; the AM335x target flags are fixed in the script.

find $PRU_CGT/bin/clpru→compile each file to obj/*.object→link with libc.a→write .out and .map
$ PRU_CGT=/usr/share/ti/cgt-pru scripts/build.sh out/fw.out AM335x_PRU.cmd main.asm
Compiling main.asm
Linking out/fw.out
Built out/fw.out (map: out/fw.map)

Fails fast with an install hint when clpru or the linker file is missing. Inside an OpenPRU checkout the repo makefiles replace it.

simulate.py

steps 6–7 · needs pru-simulator

A thin wrapper over TI's simulator that prints the same fixed summary every time. Finds the simulator through PRU_SIM_DIR, ./pru-simulator or ~/pru-simulator.

run: end state

$ simulate.py run uart_tx.asm --target am263x
target:       am263x  core: pru0
result:       PASS (halted)
cycles:       34735 (stall 0, instructions 34735)
halted:       True  pc: 20
registers≠0:  r30=0x00000002

Stops at halt or a condition: cycles>=N, reg:rN==V, mem32:ADDR==V, gpi:N==V, gpo:N==V.

edges: pin timing

$ simulate.py edges uart_tx.asm \
    --target am263x --pin 1 --edges 6
pin 1 edges (cycle, level):
  [(1,1),(8,0),(1744,1),(3480,0),(5216,1),(6952,0)]
cycles between edges:
  [7, 1736, 1736, 1736, 1736]

Runs until pin N changes, N times, and prints the cycle gaps.

Exit 0 ok, 2 load error, 3 condition unmet or budget spent, 4 simulator error, 5 simulator not installed. Models AM243x and AM263x only, at one cycle per instruction.

The simulator tools

The pru_* tools come from the pru-simulator MCP server (set up per references/simulator.md). They keep a core alive between calls, so Claude can stop, look and continue, which simulate.py cannot do.

Load

  • pru_load: assemble source text onto a core
  • pru_elf_load: load a clpru .out
  • pru_reset: clear a core

Run

  • pru_step: N instructions
  • pru_run_until: halt, cycles, register, memory or pin condition
  • pru_step_multicore: two cores in lockstep
  • pru_breakpoint

Inspect

  • pru_registers: all 32 plus carry
  • pru_memory: read only
  • pru_io: GPO and GPI pins
  • pru_status: all cores

Stimulate and export

  • pru_set_input: drive a GPI pin
  • pru_uart_inject, pru_i2c_attach: test harnesses
  • pru_vcd_export: waveform file
QuestionUse
Does it finish, and what is left in the registers?simulate.py run
How many cycles between pin edges?simulate.py edges

Example prompt, step by step

This is eval 5 from the skill's own test set. The numbers below come from running a bit-bang UART TX program (uart_tx.asm, not shipped with the skill) through the scripts.

Here's my bit-bang UART TX for AM263x. Check in the simulator that each bit is 1736 cycles at 115200 baud.
  1. Trigger
    "bit-bang", "AM263x", "simulator" match the description. Claude calls the Skill tool and SKILL.md loads.
  2. Steps 1–2
    Target and budget. AM263x ICSS-M PRU0 at 200 MHz. 200,000,000 / 115,200 = 1736.1, so the budget is 1736 cycles per bit. Claude reads references/simulator.md and timing.md.
  3. Step 4
    Lint first. lint_pru.py uart_tx.asm gives 0 error(s), 0 warning(s). The simulator reports only the first error it meets, so a clean lint avoids a confusing failure.
  4. Step 6
    Does it run to the end? simulate.py run reports PASS, halted at pc 20 after 34,735 cycles, with r30 = 0x2 (TX line idle high).
  5. Step 7
    Measure the bit time. simulate.py edges --pin 1 returns gaps [7, 1736, 1736, 1736, 1736]. The first 7 is idle setup, not a bit. Every bit is exactly 1736 cycles, matching the budget.
  6. Report
    Numbers, with the source named. "Each bit measures 1736 cycles, 8.68 µs, budget 1736, simulated on am263x." The skill's rule: under about 5% margin, recommend a hardware check. The stop bit between bytes runs a few cycles long because of per-byte setup, which UART allows.

The six pitfalls it guards against

1 · Branch order. qbgt label, r1, r2 branches if r2 > r1. Every branch costs 1 cycle, taken or not.
2 · Immediates. Most are 0–255. Use ldi or ldi32 for larger values.
3 · Zero byte count. A zero length in r0.bN hangs the core for lbbo, sbbo, lbco, sbco, xin, xout.
4 · Broadside registers. Multiplier owns r25–r29, broadside RAM owns r1–r9.
5 · Address maps. They differ per subsystem. Never reuse AM335x values on newer devices.
6 · C ABI. r2 and r3.w2 belong to the compiler, and r3.w2–r13 must be preserved.
