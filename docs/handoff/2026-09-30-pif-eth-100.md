## Findings worth remembering

- **The fractional divider makes 2x possible at n_tx = 3.** The old rule
  `n_rx = n_tx / 2` cannot work at an odd divider. RX divider 1.5
  (`div_factor` 0, FRAC 1, `RXCFG 0x0000801F`) gives a 200 MHz sample clock,
  exactly 2x oversampling of 100 Mbaud. The realtime budget is 12 core cycles per
  captured byte and poll/zero-run use 8.
- **Edge-tie sampling and the latency decision.** At 300 MHz the sample-to-edge
  offset is one of {0, 1.667, 3.333} ns, so in one third of arm phases samples
  land exactly on a TX edge. The plan preferred a 0 ns loopback latency and
  allowed 5/6 ns only as a fallback; the Task 5 second gate triggered: at 0 ns
  the edge-phase test at the 10/3 ns shift failed (`symbol_errors=71`,
  `crc_ok=0`). `LOOPBACK_LATENCY_NS` is therefore **5/6 ns**, which keeps every
  phase at least 0.83 ns from an edge. **Known limit:** decode is not robust
  when a sample edge coincides exactly with a TX edge. The 10/3 ns core period
  is inexact in floating point, so exact ties resolve inconsistently. A single
  0 ns run can pass depending on arm phase, which is not evidence that 0 ns is
  safe. Details in the README "Latency note".
- **The traced stepper; never poll `pc == label`.** `run_100.step_paced_traced`
  mirrors `Simulator.step_paced("pru0", "pru1", n)` but reports every PRU1
  instruction, so cycle-budget claims are validated by single-stepping (see
  the cycle-tight-claims lesson in the previous handoff). Do not poll
  `pc == label` between multi-instruction steps: a 2-instruction wait loop can
  alias and never match. Do not step PRU1 alone either, since it would run ahead
  of PRU0's time.
- **Fast RX equivalence.** The realtime loop is byte-identical to the baseline
  (checked with `diff`). The post-frame consumes the same bit sequence with the
  same 10-bit tiling from the same comma anchor, with the same decode,
  running-disparity and frame-buffer-guard semantics. Tests compare stats and
  frame bytes with the baseline field by field for the default seed, for seeds
  464371934 and 1 at all three edge phases, and for payload lengths 128 and 252.
  The first frame is slower (17652 cycles against about 13.5 k) because it builds
  the 256 B decimation LUT at DRAM1 local `0x0C00`.
- **80 Mbit/s is the coding rate, not the frame-averaged rate.** The wire runs at
  100 Mbaud, and 80 Mbit/s holds only while a burst is on the wire (F2). Commas,
  FCS and the inter-frame gap lower it; end-to-end F3 is bounded by RX
  post-frame work, which is why the fast RX exists.
- **UI validation is scripted only.** The user's guide was validated by a scripted
  walkthrough (base, fast, base). The real-browser click-through was **not**
  done: the Chrome extension was not connected.

## Open items

  walkthrough has been run).
- **Silicon validation** of the /1.5 fractional RX divider. Silicon may space
  sample edges unevenly (1 and 2 core clocks alternating), which would keep 2
  samples per bit at zero drift but reduce edge margin. This is not verified
  against the TRM. DRAM timing is also a simulator assumption
  (`write_latency = 1`, `jitter = 0`).
- **F3 is still bounded** by TX preparation (about 9 us between bursts, 9.05 us
  measured) and by the remaining RX post-frame work (the design spec estimated
  the BER step at about 3.4 k cycles; that figure is a spec estimate, not a
  measured breakdown).
- **Final report numbers** in `source/pif_eth_100/DEVELOPMENT_REPORT.md` are
  finalised in Task 13.
