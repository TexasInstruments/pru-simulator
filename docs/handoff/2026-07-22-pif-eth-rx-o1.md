## 1. pif_eth now has an RX path: PRU1 receives what PRU0 transmits

New design: `docs/superpowers/specs/2026-07-21-pif-eth-pru1-rx-design.md`.
PRU1 receives the 8b/10b line-coded frames PRU0 transmits over the existing
PRU0→PRU1 perif loopback, zero drift/jitter/latency, RX sample clock at
**2x the line rate** (hardware requirement — the RX shift register captures
raw oversamples, it does not decimate). Three processing depths were
specified (Option 1 raw-capture, Option 2 bit-packed, Option 3 full decode);
**only Option 1 (`pif_eth_rx_o1_raw.asm`) is implemented so far** — Options 2
and 3 remain spec-only future work.

- New files: `source/pif_eth/pif_eth_rx_o1_raw.asm`, `source/pif_eth/rx_driver.py`.
- New tests: `tests/test_pif_eth_rx.py` (13 tests as of `80229e2`).
- **This promotes `pif_eth_tx_n2.asm` / `pif_eth_tx_n2_skipchecks.asm` from
  standalone reference artifacts (previous handoff) to firmware actually
  exercised by CI** — `rx_driver.py` selects the TX variant from `n_tx`
  (`_skipchecks` only at `n_tx=2`) so the divider-hard-pin caveat from the
  previous note is now enforced in code, not just documented.
- Measured result (Task 8 of the design spec, `python3 source/pif_eth/rx_driver.py o1`):
  **all four ladder rungs pass** (`n_tx = 2, 4, 6, 8` → 125.00 / 62.50 / 41.67
  / 31.25 Mbaud), 7 seeds each, `rx_ovf=0`, `symbol_errors=0`,
  `prng_bit_errors=0`, `crc_ok=1` on every one of the 28 (rung × seed) runs.
  This was a genuine surprise against the design spec's own risk section,
  which expected `n_tx=2` might not be reachable by Option 1's 8-cycle
  budget — see [[feedback_cycle-tight-claims-need-sim-validation]], same
  lesson again: measured, not assumed.
  - **Rated divider `n_tx=2` passes at zero headroom**: 7 instructions + a
    1-cycle DRAM write stall exactly fill the 8-cycle-per-captured-byte
    budget, with none of the 4-deep FIFO's 32 cycles of slack to spare if
    that cost grows by even one cycle. Depends on this simulator's modelled
    DRAM1 timing (`config/memory_pif_eth_rx.cfg`: `write_latency=1`,
    `jitter=0`) — **a simulator measurement, not a silicon claim.**
  - `RATED_DIVIDER["o1"] = 2` in `rx_driver.py`, pinned by
    `test_o1_clean_at_rated_divider`.
  - A harness bug was found and fixed *during* characterization: the first
    draft of `characterize()` compared every rung's reconstructed frame
    against frame-0's PRNG payload regardless of `num_frames`, which fails
    for a multi-frame burst where BERT's PRNG runs continuously across
    frames. Fixed by slicing the correct final-frame window before
    comparing — a bug in the *oracle*, not the RX firmware.

## 2. Security-relevant fix: unbounded frame-buffer write

`80229e2` fixed a real overrun: the post-frame decode routine (`pf_symbol`)
wrote each decoded octet into the 256 B reconstructed-frame buffer at
`0x0E00` **without a bound**, so any `payload_len > 252` walked writes into
the stats block (`0x0F00`) and then the control block (`0x0F40`) —
poisoning `go`/`seed`/`payload_len`/`rxcfg` for whatever frame ran next.

- Fix: `pf_symbol` now stops storing at the buffer edge and sets
  `eof_status = 2` (new "overflow abort" state, alongside 0=running/
  1=clean EOF) instead of continuing to write past it.
- `rx_driver.build_sim`/`run_rx` reject `payload_len > 252` with `ValueError`
  up front, so the guard above is a backstop, not the primary defense.
- New tests: `test_o1_overrun_sets_eof_status_2_and_preserves_control_block`,
  `test_run_rx_rejects_oversized_payload_len`, `test_max_payload_len_boundary`.
- **Deliberately left unguarded:** the realtime `poll`/`zero_run` capture
  loop (the one at zero cycle headroom, above) — adding a bounds check there
  would blow its 8-cycle budget. The raw capture buffer (`0x0800`, 1024 B)
  has no firmware-side guard for the same reason; it relies on the host-side
  `payload_len` check (which also validates estimated capture size) to stay
  within bounds in practice.

## Notes for future work

- Options 2 (`pif_eth_rx_o2_bits.asm`, bit-packed) and 3
  (`pif_eth_rx_o3_decode.asm`, full 8b/10b decode) are speced but not
  implemented — see §6.2/6.3 of the design doc for the fixed-shift-unrolled
  approach expected to sustain `n_tx=4/6` and `6/8` respectively.
  `pif_eth_rx_o1_raw.asm` already covers the full ladder, so these are lower
  priority now than originally scoped — they'd mainly reduce post-frame CPU
  work, not unlock a rate Option 1 can't already reach.
- `source/pif_eth/PROJECT_REPORT.md` still needs an RX section (only
  `README.md` has one) if the project report is meant to stay the
  authoritative single-document summary.
- Non-zero drift/jitter/latency on the RX loopback is explicitly out of
  scope — §5.1/§5.2 of the design doc's simplifications (phase-insensitive
  decimation, zero/one-byte EOF proxy) both depend on zero drift and must be
  re-derived before reuse under drift.
- Striping across perif channels 1/2 and the broadside CRC accelerator
  remain unchanged future-work items from the 2026-07-20 handoff.
