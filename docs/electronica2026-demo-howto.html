electronica 2026 · LP-AM243 · ICSSG0 PRU0

Booth demos: how to run

For booth staff. Three PRU demos run on the AM243x LaunchPad (LP-AM243), each with its own PicoScope setup. Two more, PDM audio and the SPI link, run in the simulator alone, with no board and no PicoScope.

AI2C IO expander

A PRU bit-bangs 1 Mbit/s I2C. One LED runs along 8 LEDs, the PicoScope decodes the bus, and a PC window lights the same LED.

PicoScope: logic analyzer (D0/D1) BUART RX frames

A PRU receives 4 Mbaud UART frames. HelloWorld! fills the PRU memory, shown in CCS.

PicoScope: signal generator (AWG) CUART print

A PRU sends Hello 2026 as 115200 baud UART, every 1.87 ms. The PicoScope decodes the text.

PicoScope: logic analyzer (D0) DPDM audio

PRU1 synthesises two PDM microphones from audio clips, PRU0 decodes them into 16 kHz audio. Two live spectrograms show speech and a chirp.

Simulator only SPISPI link

PRU0 and PRU1 talk SPI in the simulator, frame by frame, in a loop. No board, no PicoScope.

Simulator only, runs unattended
One board demo at a time

Demos A, B and C all use ICSSG0 PRU0. To switch, load the other demo's R5F program (see Switching between demos).

The source code is in the open-pru repository, under examples/electronica2026/. Until the PRs are merged, each demo exists only on its own branch.

Wiring (all demos, can stay connected)

All wires can stay connected. Demo A does not touch BP.31, Demo B does not touch BP.32/33, and Demo C uses only BP.33, the wire that already goes to PicoScope D0 for Demo A.

The LaunchPad headers are labelled with BoosterPack (BP) pin numbers. There is no "J4.10" or "J4.8"; use the BP numbers below.

TCA9538 board: A1 = A0 = high (address 0x23), RESET high, LEDs with series resistors on P0 to P7. No I2C pull-ups needed. During Demo C the TCA9538 sees the UART signal on its SCL pin; ignore the LEDs then.

A

I2C IO expander

PicoScope as logic analyzer

PicoScope setup

  1. Signal generator: Off.
  2. Digital inputs: enable D0 (SCL) and D1 (SDA).
  3. Trigger: Pulse width, source D0, positive pulse longer than 1 µs, mode Repeat, pre-trigger about 20 %. SCL only stays high that long in the 100 ms pause between frames, so every capture starts with one frame.
  4. Timebase: about 100 µs across the screen.
  5. Preferences → MCP server (beta): On for current session, port manual 18123.
  6. Serial decoder: I2C, Data = D1, Clock = D0, Fast-mode Plus (1 Mbit/s). If you skip this, the LED window adds one named TCA9538.

Run

  1. In CCS, load and run the R5F program i2c_io_am243x-lp_r5fss0-0_freertos_ti-arm-clang. The UART console prints I2C IO expander: ICSSG0 PRU0 running.
  2. Start the LED window: 
    cd examples/electronica2026/i2c_io_expander/visualizer
./target/release/i2c_led_visualizer

    (cargo run --release also works; run source ~/.cargo/env first if cargo is not found.) Place it next to PicoScope; F11 = fullscreen.

What good looks like

  • LEDs: one LED runs P0 → P7, one step every 100 ms (0.8 s per round).
  • PicoScope: one frame per capture, decoded as 23 W 01 xx, with xx walking 01, 02, 04 … 80. The SCL period is about 1 µs.
  • LED window: status last frame: addr 0x23 · reg 0x01 · data 0x08 (the value changes), with the same LED lit as on the board.

B

UART RX frames

PicoScope as signal generator
Important

This receiver is timed for a 4 Mbaud sender that is exact or slightly slow. The AWG file is exact.

PicoScope setup

Set the values in this order, because the allowed offset range depends on the amplitude:

  1. Signal generator: waveform Arbitrary. Import helloworld_4mbaud_awg.csv from the copy outside the repository, and apply it in the editor before you close it.
  2. Amplitude 1 V (set this first).
  3. Offset +1 V. The output now swings between 0 V and 2 V.
  4. Frequency 20 kHz. Check the unit: kHz, not MHz. At 20 MHz the output looks like a sine wave and nothing is received.
⚠ Protect the input

Do not connect BP.31 while the settings are wrong. With offset 0 V the output goes below 0 V, which the LaunchPad input is not rated for.

Run (the start order matters)

The firmware has no frame sync. It cuts frames every 11 bytes from the first start bit it sees, so the line must be idle when the PRU starts.

  1. Switch the signal generator to DC, +2 V (line idle high).
  2. In CCS, load and run the R5F program uart_rx_am243x-lp_r5fss0-0_freertos_ti-arm-clang. The UART console prints UART RX frame: ICSSG0 PRU0 running, frames at PRU0 DRAM0 (0x30000000).
  3. Switch the signal generator to Arbitrary (the settings above).

Show the result in CCS

Open a Memory Browser:

  • Received frames: address 0x30000000 from the R5F, or address 0 in Data_Memory of the PRU0 debug view. Set format Packed Char. It shows He ll oW or ld !H el lo Wo rl d! …, which is HelloWorld! repeating, starting with H at the first byte.
  • Frame count: 16-bit value at 0x30000FFC. It goes up by about 20,000 per second, so it rolls over every few seconds. It only needs to change between two refreshes.
  • Error flag: byte at 0x30000FFE. It must be 0.

If something is wrong

You seeDo this
AWG output looks like a sineThe frequency is in MHz. Set 20 kHz. If it still looks wrong, import the CSV again and apply it in the editor.
Offset cannot be set to +1 VLower the amplitude to 1 V first.

C

UART print

PicoScope as logic analyzer

PRU0 bit-bangs a UART transmitter: 115200 baud, 8N1, on BP.33. It sends Hello 2026, keeps the line high for 1 ms, and sends it again, forever. There is no receiver on the board; the PicoScope is the receiver.

PicoScope setup

  1. Signal generator: Off.
  2. Digital inputs: enable D0. D1 can stay on; Demo C does not use it.
  3. Serial decoder: UART/RS-232 on D0, 115200 baud, 8 data bits, no parity, 1 stop bit, LSB first, idle high.
  4. Trigger: Pulse width, source D0, positive pulse longer than 500 µs, mode Repeat, pre-trigger about 10 %. The only high level that long is the 1 ms gap after each string, so every capture starts at the first character. Inside the string the line is never high for more than 78 µs.
  5. Timebase: about 1 ms across the screen. The string lasts 871 µs.
No digital inputs?

Channel A on BP.33 works the same way (DC, ±5 V, decoder and trigger on A, threshold about 1.65 V).

Run

  1. In CCS, load and run the R5F program uart_print_am243x-lp_r5fss0-0_freertos_ti-arm-clang. The UART console prints UART print: ICSSG0 PRU0 running, 115200 8N1 TX on PRG0_PRU0_GPO0 (BP.33).

The start order does not matter: the transmitter repeats, and the trigger waits for the gap.

What good looks like

  • PicoScope: every capture decodes as 48 65 6C 6C 6F 20 32 30 32 36, shown as Hello 2026, with no framing errors. One character lasts about 87 µs; the string repeats every 1.87 ms.
  • CCS Memory Browser: address 0x30000000, format Packed Char, shows Hello 2026 followed by a 0 byte. The PRU reads the text from there on every pass.

Optional: change the text live

Because the PRU reads the string from memory on every pass, you can type a new one in the CCS Memory Browser at 0x30000000. The PicoScope shows it from the next pass on (within 2 ms).

  • End the text with a 0 byte, or the PRU keeps sending what follows in memory.
  • At most 255 bytes.
  • Not yet tried on hardware. If it does not work, reload the R5F program to get Hello 2026 back.

D

PDM audio

Simulator only

PRU1 synthesises two PDM microphones from audio clips (two 2nd-order sigma-delta modulators, 3.072 MHz PDM clock). PRU0 decodes them through the ICSS sigma-delta hardware (SINC3 filter, then a 63-tap FIR) into 16 kHz PCM. The dashboard's Audio view shows both channels as live spectrograms. Every PRU cycle is simulated, so the picture builds up slowly: about 1.5 ms of audio per second.

Run

  1. Start the dashboard from the pru-simulator folder (branch electronica2026-demos): 
    python3 ui/server.py      # then open http://127.0.0.1:8080/
  2. Open the Audio tab.
  3. Pick Gen L speech_librivox.wav and Gen R chirp_lin_100_7000.wav. Swap L↔R exchanges them.
  4. Click Run. The first setup sets both PRU clocks to 200 MHz and shows a notice; that is expected.
  5. Click Booth for the large view: only the clip pickers, Run/Stop and the two spectrograms. Exit booth or Esc leaves it.

What good looks like

  • The first spectrogram column appears after about 11 s (it needs 16 ms of audio). After that a new column (8 ms of audio) follows about every 5 s.
  • Left: speech formants. Right: the chirp ridge climbing from 100 Hz to 7 kHz.
  • The progress bar moves and Simulation speed reads about 1.5 ms audio / s.
  • The 450 ms speech clip takes about 5 minutes. The 250 ms chirp ends after about 2 min 50 s, so the right side stays blank from then on while the left keeps going. Then the run stops; click Run to start again from 0.

Talking points

  • Two PRU cores, one data line: both microphones share one PDM data line. The left mic is valid on the rising clock edge, the right mic on the falling edge, like a real stereo PDM pair.
  • Exact clock: 3.072 MHz from a 200 MHz core is 65 + 5/48 cycles per period. PRU1 mixes short and long periods so there is no drift, only 5 ns jitter.
  • Headroom: the PRU0 receiver needs at most 1009 of the 6250 cycles per sample window for 2 channels (16 %). 8 channels are estimated at about 64 %.
  • Every cycle simulated: that is why it is slow. The same receiver code was then ported to the LP-AM243 (open-pru PR #191).

SPI

SPI link

Simulator, runs unattended

PRU0 is an SPI controller and PRU1 an SPI peripheral, both bit-banged and wired pin to pin in TI's pru-simulator. Visitors watch frames go across a scope bit by bit: walking 1, walking 0, 0xA5 / 0x5A and 00 / FF, about 7 s per frame and about 30 s per loop, repeating. No board or PicoScope is needed, so it can run on its own laptop or screen next to the board demos.

The code is in pru-simulator, branch feat/spi-pru-link (PR #108). Until the PR is merged, use branch electronica2026-demos (see the top of this page).

Run (two clicks)

  1. Start the dashboard from the pru-simulator folder: 
    python -m ui.server      # then open http://localhost:8080
  2. Go to I/O & Devices → SPI.
  3. Click Set up SPI demo.
  4. Click ▶ Play.

Play runs the SPI test sequence once (about a second), then replays its frames in a loop. While it plays, every SPI control except Pause and Speed is greyed out, so a visitor clicking around cannot stop it.

What good looks like

  • A row of 21 green ✓ chips above the frame strip. The 4 loop frames have a thicker green border, and the one playing is outlined in yellow.
  • The line above the frame strip names the step, for example Step 6/21 · rw:walking1 · READ/WRITE (03) @ 0x41 · pattern walking1.
  • The scope trace draws left to right, the byte boxes fill in as each byte completes, and the PRU1 RX and PRU0 RX panels fill byte by byte. The compare badge reads Transferring…, then 16/16 bytes match both ways at the end of each frame.
  • Speed: booth is the default. slow halves the pace and fast triples it.

Talking points

  • Real pin trace: what is drawn is the simulator's recorded pins (/CS, CLK, MOSI, MISO), not an animation.
  • Two PRU cores: PRU0 drives SPI CLK at 25 MHz on a 200 MHz core (5 ns per cycle). PRU1 follows every clock edge.
  • Timing table: below the scope, with the AM243 datasheet values marked. The tightest margin (MISO setup) is flagged.
  • Tested up to 50 MHz: the link was swept from 10 to 50 MHz in both SPI modes. 50 MHz works at a 300 MHz core.

Switching between demos

  1. Stop the current demo:
    • A close the LED window.
    • B set the signal generator to Off or DC +2 V.
    • C nothing to stop.
  2. In PicoScope, switch to the other demo's settings (open the saved settings file, or use the table at the top).
  3. In CCS, do a system reset of the board, or power-cycle it. Then load and run the other demo's R5F program. It loads its own PRU0 firmware.
  4. For Demo B, keep the start order: DC +2 V → run R5F → Arbitrary.

The wiring can stay as it is.

The simulator demos (D and SPI) do not touch the board; see SPI link and audio on two screens for switching between them.
