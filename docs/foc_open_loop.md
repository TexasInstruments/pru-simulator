# FOC Open-Loop (V/f) PWM Example

`source/foc_open_loop.asm` is ordinary PRU0 assembly: an open-loop FOC ("level
1") controller that ramps a speed reference, integrates the electrical angle,
applies the inverse Park transform to Vd/Vq references and produces
three-phase space-vector PWM on `R30.0`-`R30.2`. It polls the simulator's IEP
counter and starts each period every 12,500 IEP ticks. With the shipped 200 MHz
IEP clock that is 62.5 us, or 16 kHz. The firmware requires matching 12,500-tick
control and PWM periods.

There is no simulator fast path or callback: the firmware executes instruction
by instruction (`cycles == instructions + stall cycles`), and the motor
plant is coupled to it only through the real pins.

```
host --ABI block (0x00010100)--> firmware --R30.0-2 PWM--> foc_motor model
                                    ^                          |
                                    +----- GPI3/GPI4 PDM <-----+  (phase A/B current)
```

## Control loop

Each control update (every PWM period, while all PWM outputs are low):

1. adopt a new control block if `requested_generation` changed;
2. ramp the speed toward `speed_ref` by at most `ramp_rate` per update;
3. `angle += speed` (32-bit phase accumulator, one turn = 2^32);
4. look up sin/cos in a 1024-entry Q15 table (nearest entry, +/-0.18 deg);
5. inverse Park, `alpha = vd cos - vq sin`, `beta = vd sin + vq cos` (Q15,
   on the MAC accelerator);
6. TI `SVGEN_runCom` phase order with common-mode injection, centered phases
   clamped to +/-sqrt(3)/4 (the clamp sets `STATUS_SATURATED`);
7. compare values for the next period; outputs are neutral (all duties 0.5)
   while disabled or after an invalid config, and the ramped speed resets to 0.

The sine table is generated by the firmware itself at start-up (about 24,600
core cycles) with the recurrence `s[k+1] = 2 cos(d) s[k] - s[k-1]` in Q30,
stored at PRU0 DRAM0 `0x1000-0x1FFF` as 1024 signed Q15 words (max error under 1
LSB). The host does not seed anything.

The phase order and common-mode convention match TI's
[`SVGEN_runCom`](https://software-dl.ti.com/processor-industrial-sw/esd/motor_control_sdk/am243x/2025_00_00_06/docs/api_guide_am243x/svgen_8h_source.html).

### Timing

At the shipped 250 MHz PRU0 and 200 MHz IEP clocks the saturated-vector
low window is 838 IEP ticks, or 1,047 PRU cycles. The worst measured control
update (the one that adopts a new generation) takes 233 PRU cycles including
19 stall cycles; steady-state updates take 190-200 cycles and a disabled update
106. The test requires the update to use less than half of the window. The
period measured on the pins stays within 12 cycles (50 ns) of 62.5 us,
including across IEP counter rollover.

## Control ABI

The schema `schema/foc_control_abi.json` generates the Python packer
(`pru_io/foc_control_abi.py`) and assembly constants
(`source/foc_control_abi.inc`). Check or regenerate them with:

```bash
python -m tools.gen_foc_abi --check
python -m tools.gen_foc_abi
```

The little-endian block is at `0x00010100` (ABI version 2, 48 bytes):

| Offset | Field | Type | Default | Owner | Meaning |
|---|---|---:|---:|---|---|
| `0x00` | `abi_version` | u32 | 2 | host | Firmware/config compatibility |
| `0x04` | `control_period_ticks` | u32 | 12,500 | host | Control update interval (fixed) |
| `0x08` | `pwm_period_ticks` | u32 | 12,500 | host | PWM period (fixed) |
| `0x0C` | `enable` | u32 | 0 | host | 1 runs the controller, 0 holds neutral output |
| `0x10` | `requested_generation` | u32 | 0 | host | Change this to publish the block |
| `0x14` | `speed_ref_q28` | s32 | 0 | host | Signed electrical speed, 1 pu = 2^28 |
| `0x18` | `ramp_rate_q28` | u32 | 2^28 | host | Max speed change per update (2^28 = no ramp) |
| `0x1C` | `vd_ref_q15` | s32 | 0 | host | d-axis voltage, 1 pu = 32,768 |
| `0x20` | `vq_ref_q15` | s32 | 0 | host | q-axis voltage, 1 pu = 32,768 |
| `0x24` | `initial_phase_q32` | u32 | 0 | host | Starting angle (read once, at the first update) |
| `0x28` | `ack_generation` | u32 | - | PRU | `requested_generation` last adopted |
| `0x2C` | `status` | u32 | - | PRU | 1 running, 2 invalid config, 4 saturated |

**Handshake.** The firmware compares `requested_generation` with the last one
it adopted at every control update. Only a changed generation makes it re-read
the block, so a multi-field change is adopted atomically; writing a field
without bumping the generation has no effect. The host writes the other fields
first and the generation last (`pru_io/foc_control.stage_control` does this and
never writes the PRU-owned words). After adoption the firmware writes
`ack_generation`; `status` is refreshed every update. Out-of-range values, a
wrong `abi_version` or non-default periods set `STATUS_INVALID_CONFIG`, keep
the output neutral and are still acknowledged; the next valid generation
recovers. `pack_config` rejects the same ranges on the host.

**Units.** Speed is electrical, per unit of a 1 kHz base:
`speed_q28 = rpm * pole_pairs / 60 / 1000 * 2^28`, so 1 pu advances the angle by
1/16 turn per 16 kHz update. `ramp_rate_q28` is the speed change per update:
`rpm_per_s * pole_pairs / 60 / 1000 / 16000 * 2^28`. Voltages are per unit of
the DC bus: a Vd/Vq vector of magnitude 1 pu is a phase amplitude equal to
`Vdc`; the linear limit is 1/sqrt(3) = 0.577 pu, beyond which the centered
phases clamp. `pru_io/foc_control.py` has the conversions
(`speed_rpm_to_q28`, `ramp_rpm_s_to_q28`, `voltage_pu_to_q15`).

At angle zero `vd`/`vq` are the alpha/beta inputs of `SVGEN_runCom`; the tests
use that identity for the TI vectors and compare every other angle, speed and
ramp against an independent pure-Python Park + SVGEN reference.

## Pin-coupled PMSM model

The optional `foc_motor` `DeviceModel` (PRU0 only) observes the real GPO0-2
bus and has no shared-memory path to or from the firmware. Its profile sets the
core's GPO drive mask to `0x7`, so it cannot share PRU0 with another device.

Equations (surface-mounted, Ld = Lq, floating neutral, per integration step of
at most 5 us of core time):

- pole voltages `(pole - mean(pole)) * Vdc`, Clarke to `valpha, vbeta`
- `L di/dt = v - R i - e`, `e_alpha = -lambda w_e sin(theta_e)`, `e_beta = lambda w_e cos(theta_e)`
- `iq = -i_alpha sin(theta_e) + i_beta cos(theta_e)`, `Te = 1.5 p lambda iq`
- `J dw/dt = Te - B w - T_load`, `theta_e += p w dt`

`T_load` is an external torque that opposes positive rotation. With
`flux_linkage_vs = 0` the model is the previous pure three-phase RL load.
The phase currents are held between plant steps (at most 5 us), then the two
sigma-delta modulators sample ia/ib at their own clocks (20 MHz by default).
Currents are clamped to `current_limit_a`.

| Option | Default | Runtime | Meaning |
|---|---:|:---:|---|
| `resistance_ohm` | 0.5 | yes | Phase resistance (> 0) |
| `inductance_h` | 0.001 | yes | Phase inductance (> 0) |
| `flux_linkage_vs` | 0.05 | yes | PM flux linkage = Ke in V*s/rad electrical (>= 0) |
| `pole_pairs` | 4 | yes | 1-64 |
| `inertia_kg_m2` | 0.0005 | yes | Rotor + load inertia (> 0) |
| `damping_nm_s` | 0.003 | yes | Viscous damping (>= 0) |
| `load_torque_nm` | 0.0 | yes | Constant load torque |
| `dc_bus_v` | 48.0 | yes | DC bus voltage (> 0) |
| `current_scale_a` | 20.0 | no | PDM full scale |
| `current_limit_a` | 40.0 | no | Current clamp |
| `current_a_pin`, `current_b_pin` | 3, 4 | no | PDM output pins |
| `current_a_clock_hz`, `current_b_clock_hz` | 20 MHz | via SD routes | PDM sample clocks |

Runtime changes use the generic `DeviceModel.configure(parameters)` contract,
exposed as the MCP tool `pru_device_configure(device_name, parameters)`. A
change is validated as a whole (unknown names, non-finite or non-positive
values and bad pole counts are rejected without changing anything) and applies
from the next plant step. Snapshots include the parameters, so step-back
restores them. `configure` also accepts the display-only
`reference_angle_rad` (below).

### What is measured from the pins and what is plant state

Pin-derived, per PWM period (the all-low to any-high transition starts a
period): on-time of each phase gives `duty_cycles`; the average pole voltages
give `alpha_beta_v`; `pwm_frequency_hz` is the core clock over the period;
`voltage_angle_rad` is `atan2(beta, alpha)`; `commanded_angle_rad` is that
angle minus `reference_angle_rad`; `commanded_speed_rpm` is the rate of the
unwrapped commanded angle over the last 32 periods divided by the pole pairs.
`reference_angle_rad` is the angle of the (Vd, Vq) reference, `pi/2` by default
(pure Vq); it only labels the reported angle and never enters the physics, so
a host that sets Vd must also set it (`atan2(vq, vd)`). A neutral (zero-vector)
output keeps the last angle.

Plant state: `rotor_angle_rad` (electrical), `rotor_speed_rpm`,
`phase_currents_a`, `id_a`, `iq_a`, `torque_nm`. `angle_error_rad` is the
commanded angle minus the rotor angle, wrapped to +/-pi. The model also keeps a
bounded ring (1,024 per-period samples) with a monotonically increasing index:
`samples_since(index)` returns the fields in `SAMPLE_FIELDS`, `next_index` and
how many requested samples were `dropped`.

## Run with the MCP wrapper

```python
from pathlib import Path

from mcp_server.server import PRUSimulatorMCP
from pru_io import foc_control as foc

mcp = PRUSimulatorMCP("memory.cfg")
mcp.pru_device_attach(profile="foc_motor", config={"load_torque_nm": 0.0})
mcp.pru_sd_route_input(channel=0, pin=3)
mcp.pru_sd_route_input(channel=1, pin=4)
foc.stage_control(
    mcp.sim.memory, enable=1,
    speed_ref_q28=foc.speed_rpm_to_q28(400, pole_pairs=4),
    ramp_rate_q28=foc.ramp_rpm_s_to_q28(1000, pole_pairs=4),
    vq_ref_q15=foc.voltage_pu_to_q15(0.15),
)
source = Path("source/foc_open_loop.asm").read_text(encoding="utf-8")
mcp.pru_load(source, include_paths=["source"])
mcp.pru_step(count=200_000)
print(mcp.pru_device_state()["devices"][0])
mcp.pru_device_configure("foc_motor", {"load_torque_nm": 0.2})
```

There is no MCP tool that writes shared memory; stage the control block from
Python as above (or from the dashboard). Reference changes while running use
`stage_control` again.

The simulator runs the bus per elapsed core cycle, so a device-attached run
advances roughly 40,000 PRU cycles (one 16 kHz period is 15,625) per wall
second. Motor mechanics that take hundreds of milliseconds therefore need
minutes of wall time; the plant physics are tested with a scaled clock instead.
Disconnect the model with `mcp.pru_device_detach("foc_motor")` to restore the
previous GPO drive mask.
