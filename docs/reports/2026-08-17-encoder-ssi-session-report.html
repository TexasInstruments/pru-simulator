3 Design Choices

The implementation focused on creating complete, well-documented SSI encoder simulator support that follows the same patterns as existing projects like pif_eth and i2c_tca9538_running_led. Key decisions included:

Documentation Structure Decisions

3.1

Separate README.md and PROJECT_REPORT.md for each SSI project

Following the established pattern: README for user-focused quick start, PROJECT_REPORT for developer-focused deep dive on design decisions and implementation details.

3.2

Implementation-focused session report

Rather than documenting the documentation process, the report focuses on the actual implementation: firmware, emulators, MCP tool, validation methods, and usage instructions.

3.3

Generic documentation skill in docs/skills/

Moving the skill from local configuration into docs/skills/ ensures it's available to all users of the repository.

Technical Implementation Decisions

3.4

SSI Reader requires 300 MHz PRU core clock

To achieve exact 4 MHz SSI clock (75 cycles/bit), avoiding non-integer ratios and timing drift that occurs at 200 MHz.

3.5

Purely reactive SSI emulators

Using wbc/wbs instructions for edge detection makes emulators robust to master clock frequency variations without timing constant adjustments.

3.6

MCP injection tool for single-core validation

Eliminates the need for a second PRU during development/testing by attaching SSIEncoderGenerator to the selected simulator IO port.

3.7

Standardized memory maps matching hardware projects

Ensuring PRU1 DRAM1 offset 0x10 for the captured word and PRU0 DRAM0 offsets 0x08 (value) and 0x14 (frame counter) match the current simulator role assignment and hardware project layouts for cross-validation.

Validation Strategy Decisions

3.8

Multi-layered validation approach

Combining automated regression test, manual UI validation, and single-core MCP validation ensures correctness at multiple levels.

6 Testing and Validation

The implementation includes multiple validation layers to ensure correctness.

6.1 Automated Regression Test

The sequence emulator test validates end-to-end dual-core capture:

python -m pytest tests/test_ssi_encoder_sequence_emulator.py -v

This test loads the SSI reader on PRU1 and sequence emulator on PRU0, wires the GPIO loopback, and verifies all five test values (0xABC → 0xAAA → 0xBCA → 0x12A → 0xCC2) are captured in order at DRAM1 offset 0x10.

6.2 Manual UI Validation

Validation using the browser-based simulator dashboard:

  1. Start dashboard: python ui/server.py
  2. Load SSI reader on PRU1
  3. Load sequence emulator on PRU0
  4. Configure GPIO loopback:
    • PRU1 GPO0 (clock out) → PRU0 GPI16 (clock in)
    • PRU0 GPO0 (data out) → PRU1 GPI8 (data in)
  5. Enable Signal Graph recording
  6. Run multi-core execution
  7. Observe clean 12-clock SSI transitions in both clock lanes
  8. Use "Fit frame" to zoom to newest complete SSI frame
  9. Verify DRAM1 offset 0x10 matches expected sequence value
  10. Check frame counters increment on both cores

6.3 Single-Core Validation via MCP

Quick validation without requiring a second PRU emulator:

python3 -c " from mcp_server.server import PRUSimulatorMCP mcp = PRUSimulatorMCP() result = mcp.pru_ssi_inject( source=open('source/ssi_reader_4mhz_12bit/ssi_reader_4mhz_12bit.asm').read(), value=0xABC, clk_pin='GPO0', data_pin='GPI8', core='pru1' ) print(f'Expected: 0x{result[\"expected\"]:03X}') print(f'Captured: 0x{result[\"captured\"]:03X}') print(f'Match: {result[\"match\"]}') print(f'Frames: {result[\"frames_captured\"]}') "

Should return match=true for test values 0x000, 0xA5A, and 0xFFF.
