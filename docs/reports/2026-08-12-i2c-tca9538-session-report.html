3 Design Choices

The simulator had no I2C concept before this session — only raw GPIO and a generic bit-mirror loopback. Every decision below either scopes that gap or was forced by something the gap turned out to hide.

Decided up front, via Q&A before any code was written

3.1

Full TCA9538 device model, not firmware-only

A bit-bang master with no slave to talk to can't produce a real ACK or a visible LED. Chose to build a genuine I2C-slave state machine in Python — closed-loop: wrong address really NACKs, output pins are really observable — over the cheaper option of just eyeballing the waveform.

3.2

200 MHz core clock, address 0x23

200 MHz matches the simulator's existing SPI example and default core speed, and divides cleanly into 200 cycles/bit at 1 Mbit/s. 0x23 is an arbitrary but conventional TCA953x address, fine since both sides of the link are code under our control.

3.3

SCL = bit 0, SDA = bit 1, true open-drain semantics

Write 1 to release a line, write 0 to drive it low — matching real open-drain I2C pads, not push-pull GPIO. The bus level is the wired-AND of every driver, computed fresh in IOPort from whichever devices are attached.

3.4

Attach is opt-in, never default-on

Bits 0/1 already mean SCLK/MOSI to the existing spi_master_tx.asm example. An always-on device would silently corrupt that program's GPI reads, so the TCA9538 model only exists on a session when explicitly attached — mirroring how loopback groups already work in this UI.

3.5

Dashboard panel, auto-appearing on first START

Follows the same pattern as the existing Sigma-Delta filter panel: hidden until the peripheral shows real activity, then it takes over its section of the IO panel — 8 LEDs plus a decoded-transaction log line.

Found and corrected during implementation, via task review

3.6

A DONE state, to separate "this byte just got ACKed" from "a real second-byte violation"

The first state-machine draft treated a data byte's own ACK-completion edge as if it were an aborted second byte — it would have flagged every successful write as a failure. Caught in self-review before implementation even started; the design doc's state diagram was rewritten to add a dedicated DONE state before Task 1 was dispatched.

3.7

START/STOP detection keyed off the master's own SDA line, not the post-wired-AND bus level

An implementer's first pass at the state machine produced a real false-START bug: when the slave began driving its own ACK immediately after the master's last bit was a 1, the bus level fell in a way that looked exactly like a START condition. The fix tracks the master's raw SDA signal separately from the wired-AND result used for ACK sampling — eliminating the false positive without weakening STOP's "works from any state" guarantee that later tests depend on.

3.8

Firmware timing tests pinned to a 200 MHz fixture, not the dashboard's live clock setting

This project's test suite already has a documented gotcha: a bare Simulator() inherits whatever core speed the dashboard's UI last had selected. Firmware tests here use the nominal_config fixture specifically so the 1 Mbit/s timing assumptions can't silently drift.

3.9

Init-time NACK halts; run-loop NACK sets a sticky flag and continues

Nothing useful can happen if the initial Configuration write never lands, so that path halts outright. A NACK mid-animation is treated as a soft, recoverable bus fault — it flags DRAM0 and moves on to the next pattern value rather than freezing the LED show.

3.10

Core-switch handler now detaches the device on the outgoing core

Caught only in the final whole-branch review, after every individual task had already passed its own review: switching cores in the dashboard left a TCA9538 wired to the core you left, silently corrupting any other bit-banged program loaded there afterward. No single task owned the core-switch handler, so no task-scoped review could have seen it — this is exactly the kind of cross-cutting gap a final integration pass exists to catch.
